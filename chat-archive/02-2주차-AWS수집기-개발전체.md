## 2. 핵심 개념 (사용자가 "이론을 모르겠다" 해서 설명한 것)

**출입증(인증)이 두 개인 이유:**
- 문 A — `finops-collector` (IAM 사용자, 1주차): 내 노트북이 AWS에 "데이터 보여줘" 물어볼 때 쓰는 **읽기 전용** 출입증.
- 문 B — `CloudWatchAgentRole` (IAM 역할, 오늘 신규): 인스턴스 자신이 "내 메모리가 이만큼" 보고할 때 쓰는 출입증.
- CPU는 AWS가 밖에서 볼 수 있어서 문 A로 조회 가능. 메모리·디스크는 컴퓨터 "속" 사정이라 AWS가 못 봄 → 안에 감시병(CloudWatch Agent) 심어서 직접 보고. 감시병도 증명(문 B)이 필요. 처음에 문 B를 안 줘서 `NoCredentialProviders` 에러.

**Namespace와 Dimensions:**
- Namespace = 서랍장 이름. `AWS/EC2`(AWS 기본) vs `CWAgent`(우리 감시병이 채움).
- Dimensions = 서랍 안 정확한 칸. 메모리는 InstanceId 하나면 됨. **디스크는 InstanceId + path(`/`) + device(`nvme0n1p1`) + fstype(`xfs`) 4개 전부 일치해야 조회됨.**

**normalize가 필요한 이유:** AWS·Azure·GCP가 각자 다른 모양으로 데이터를 줌. 한 DB에 같이 쌓으려면 컬럼명·단위·타임스탬프 통일. `to_common_record()`가 팀 약속 모양(`cpu_avg`, `memory_avg`, `disk_avg` 등)으로 다시 포장.

**단위 테스트:** AWS에 진짜 연결 안 하고 가짜 값 넣어서 포장 함수 로직만 빠르게 검증(느리고 돈 드는 실호출 대신).

**stress-ng:** 수집기가 "실제 부하 변화"를 잡아내는지 검증. 저활용→정상→과부하 3단계.

## 3. 실제 진행 순서

## 4. Ubuntu vs Amazon Linux 결정
팀장 계획서는 Ubuntu 기준이지만 우리 인스턴스는 Amazon Linux.
→ 수집 코드는 boto3 API 호출만 하므로 대상 인스턴스 OS는 코드/데이터 병합과 무관.
전환 시 Agent/IAM 재설정 비용만 크고 이득 없음 → **Amazon Linux 유지**. 명령어만 apt→dnf.
diary/decisions에 근거 남기기로 함.

## 5. 오래 디버깅한 부분 (stress-ng 대기가 아니라 디스크 null)
디스크 값이 계속 null → (1) 이름 잘못 짐작(`used_percent`→실제 `disk_used_percent`, 차원 4개) → (2) 여전히 null → 로그 확인 → `NoCredentialProviders` 발견(IAM 역할 미부착) → (3) 역할 부착·Agent 재시작 → (4) 시간 지나서야 값 나옴(list-metrics는 빨리 뜨지만 get-metric-statistics는 반영 지연).

## 6. runbook 핵심 (aws-collector-setup.md)
- 메모리: `Namespace=CWAgent, MetricName=mem_used_percent, Dimensions=[InstanceId]`
- 디스크: `Namespace=CWAgent, MetricName=disk_used_percent, Dimensions=[InstanceId, path, device, fstype]` **4개 전부 일치**
- 디스크 메트릭은 Agent 재시작 후 첫 반영까지 최대 10~20분 지연
- Cost Explorer는 반드시 `region_name="us-east-1"`, 5분 주기 호출 금지(호출당 $0.01)
- 검증: `python3 collectors/aws_exporter.py`, `python3 -m pytest tests/ -v`
