\## 오늘 처음 안 사실

| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |

|-----------|-----------|----------------|

| IAM 사용자 키(로컬용)와 인스턴스 역할(Agent용)이 같은 건 줄 알았음 | 완전히 별개다 | 로컬 코드는 "밖에서 AWS에 물어보는" 인증, Agent는 "인스턴스 안에서 AWS로 쓰는" 인증이라 경로가 다름 |

| list-metrics에 뜨면 바로 조회되는 줄 알았음 | 메트릭 카탈로그(list-metrics)와 실제 시계열 데이터(get-metric-statistics)는 반영 속도가 다를 수 있음 | 카탈로그는 가벼운 색인이라 빨리 뜨고, 실제 통계 데이터는 별도 파이프라인이라 더 걸릴 수 있음 |

| 디스크도 메모리처럼 InstanceId 하나면 조회되는 줄 알았음 | 디스크는 path/device/fstype까지 4개 차원이 정확히 일치해야 함 | 디스크는 마운트 지점별로 값이 다를 수 있어서 Agent가 세부 차원을 붙여서 올림 |

| 컴퓨터에 파이썬 하나만 있는 줄 알았음 | Anaconda/Python314 등 여러 버전이 섞여 있으면 명령어가 다른 환경을 가리킬 수 있음 | PATH 우선순위에 따라 `pip`/`pytest` 등이 서로 다른 파이썬을 가리킴 |

| "인스턴스 시작" 버튼이 다 같은 줄 알았음 | 주황 "인스턴스 시작" = 새로 만들기(Launch), 상태 드롭다운의 "인스턴스 시작" = 켜기(Start)로 완전히 다른 기능 | 콘솔 UI에서 두 기능에 같은 한글 표현을 씀 |

\## 막힌 점

\- CloudWatch Agent에 IAM 역할을 안 붙인 채로 시작해서 `NoCredentialProviders` 에러로 한참 헤맴 → 역할 부착 후 Agent 재시작으로 해결

\- 디스크 메트릭 이름/차원을 잘못 짐작(`used\_percent` + InstanceId만) → `list-metrics`로 실제 값 확인 후 `disk\_used\_percent` + 4개 차원으로 수정

\- 디스크 데이터가 통계 API에 반영되기까지 예상보다 오래 걸림 (list-metrics엔 바로 떴지만 get-metric-statistics는 한참 비어있었음) → 시간 두고 재시도해서 해결

\- 터미널에 긴 코드 붙여넣다가 heredoc이 중간에 끊겨서 파일 내용이 깨짐 → 메모장으로 전체 재작성해서 복구

\- 팀장 계획표(Ubuntu)와 실제 인스턴스(Amazon Linux)가 달라서 명령어 호환 고민 → 코드/데이터 병합엔 영향 없다고 판단하고 Amazon Linux 유지하기로 결정 (별도 decisions 문서화 필요)
