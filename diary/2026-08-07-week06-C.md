## 오늘 한 일
- `curl .../resources?cloud=GCP`, `.../costs?cloud=GCP`로 GCP 데이터가 서버 DB에 있는지 먼저 확인
- `docker-compose up -d grafana`로 컨테이너 기동, PostgreSQL 데이터소스 연결 (Host: `db:5432` — Grafana 컨테이너 입장에서 `localhost`는 자기 자신이라 서비스 이름으로 접속해야 함)
- Grafana 대시보드 패널 4개 구성: CPU 시계열, 클라우드별 일별 비용 바차트, 누적 비용 Stat, 최근 24시간 평균 CPU Bar gauge
- CPU 평균 80% 초과 시 발동하는 Alert Rule("CPU 과부하 감지") 생성 (폴더: CloudFit, evaluation group: cpu-alerts, 1분 간격)
- GCP VM crontab 자동화 설정: 5분마다 자원 수집, 매일 09시 비용 수집. venv 안 python3 전체 경로(`/home/user/finops-env/bin/python3`)를 명시해서 cron이 시스템 python으로 도는 것 방지
- stress-ng 정상(10분×2)/이상(5분×2)/스파이크(1분×3) 패턴을 `nohup` 백그라운드로 실행, 각 부하 직후 수동으로 exporter 실행해서 cron 5분 주기 사이에 데이터가 누락되지 않게 함

## 왜 이 기술/방법을 선택했는가
| 항목 | 선택한 것 | 대안 | 선택 이유 |
|------|-----------|------|-----------|
| Grafana 설치 방식 | docker-compose에 서비스 추가 | EC2에 native 설치(`apt`) | 프로젝트가 이미 db/server를 docker-compose로 관리 중이라 일관성 유지, `docker-compose up` 한 줄 재현성 유지 |
| stress-ng 직후 수동 exporter 실행 | cron(5분)과 별개로 부하마다 수동 실행 | cron 수집만 신뢰 | 5분 주기로는 1분짜리 스파이크가 수집 시점 사이에 껴서 통째로 누락될 수 있음 |
| cron 명령어에 venv python 전체경로 명시 | `/home/user/finops-env/bin/python3` | `python3`만 사용 | cron은 가상환경을 자동 활성화하지 않아서, 시스템 python으로 실행되며 패키지 못 찾는 조용한 실패가 날 수 있음 |

## 오늘 처음 안 사실
| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |
|-----------|-----------|----------------|
| `--costs` 옵션이 자원/비용 수집을 나누는 줄 알았음 | 옵션 유무와 상관없이 항상 자원+비용을 같이 수집함 | 코드 내부에 옵션 분기가 실제로 구현 안 되어 있었음 → 5분 cron마다 비용 API까지 매번 호출되는 상태로 방치 중 |
| `/resources` API가 전체 이력을 다 보여주는 줄 알았음 | 최근 100건 정도만 반환해서, cron이 밤새 쌓은 데이터에 옛날 stress-ng 테스트 구간이 밀려나 안 보임 | API 응답에 row 수 제한(LIMIT)이 있어서 |
| stress-ng 설정 시간(10분)이 항상 그대로 다 도는 줄 알았음 | 첫 번째 정상 패턴 실행이 39초 만에 끝남 (그 순간 여유 메모리 72MB 경고와 동시 발생) | e2-micro(RAM 1GB)에서 메모리 부족으로 조기 종료됐을 가능성 |
