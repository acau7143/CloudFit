## 오늘 목표

## 오늘 한 일
- `gcp_exporter.py`에 `requests` 기반 `send_resource_to_server()` / `send_cost_to_server()` 함수 추가
- A가 ngrok으로 로컬 서버를 임시 공개 → `gcp_exporter.py`의 `SERVER_URL`을 ngrok 주소로 교체
- 무료 ngrok이 요청마다 브라우저 경고 페이지를 거치게 해서, 코드에 `ngrok-skip-browser-warning: true` 헤더 추가
- `python3 gcp_exporter.py` 실제 실행(`--dry-run` 없이) → 자원 데이터 1건, 비용 데이터 26건 전송 성공
- `curl`로 서버 쪽 `/resources?cloud=GCP`, `/costs?cloud=GCP` 조회하여 실제 DB 저장 확인 (검증 완료)

## 왜 이 기술/방법을 선택했는가

| 항목 | 선택한 것 | 대안 | 선택 이유 |
|------|-----------|------|-----------|
| 서버 접속 방식 | ngrok 임시 터널 | 클라우드 공인 IP 배포 | 오늘 연결 검증이 급해서 빠른 방법 우선 선택. 정식 배포는 추후 과제로 남김 |


## 오늘 처음 안 사실

| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |
|-----------|-----------|----------------|
| 무료 ngrok은 그냥 터널만 뚫어주는 줄 알았음 | 요청마다 "브라우저 경고 페이지"를 한 번 거치게 해서, 자동화된 요청은 별도 헤더로 우회해야 함 | 사람 요청과 자동화 요청을 구분하려는 ngrok 무료 버전의 기본 동작 |
| `collect_cost()`가 매번 최근 7일치를 다시 조회한다는 걸 실제로 확인 | 반복 실행하면 겹치는 날짜의 비용 데이터가 중복 저장될 수 있음 (오늘 26건 중 7/21~7/24는 이전에도 조회된 적 있는 날짜) | 서버/DB에 날짜+서비스 조합 유니크 제약이나 upsert 로직이 아직 없어서 |

## 결과·증거

- 팀 작업(AWS/Azure/GCP) 전부 `main`에 병합 완료

- `curl .../resources?cloud=GCP` → GCP 자원 레코드 1건 확인

## 오늘 사용한 명령어 정리 (나중에 다시 볼 때 참고용)

**서버 연결 테스트 관련**
```bash
curl -H "ngrok-skip-browser-warning: true" <ngrok주소>/health      # 서버 살아있는지 확인
python3 gcp_exporter.py                                            # --dry-run 없이 실제 전송
curl -H "ngrok-skip-browser-warning: true" "<ngrok주소>/resources?cloud=GCP" | python3 -m json.tool   # 저장 확인
```
