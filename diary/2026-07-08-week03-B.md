## 오늘 한 일

### 1. Cost Management 비용 조회 권한 추가

기존 `finops-collector` Service Principal은 자원 메트릭 조회를 위해 Monitoring Reader 역할을 사용하고 있었다.

Azure 비용 데이터는 Azure Monitor가 아닌 Cost Management에서 조회하므로, 구독 범위에 다음 권한을 추가했다.

```text
역할: Cost Management 판독기
대상: finops-collector
범위: Subscription
```

비용을 조회하는 기능만 필요하기 때문에 비용 설정을 변경할 수 있는 참가자 역할이 아닌 읽기 전용 역할을 선택했다.

### 3. Cost Management API 첫 호출

별도 검증 코드인 `azure_cost_check.py`를 이용하여 Cost Management API를 처음 호출했다.

초기에는 Subscription 범위에서 최근 7일 비용을 Daily 단위로 조회했다.

확인된 컬럼:

```text
Cost
UsageDate
Currency
```

실제 반환 구조:

```text
[비용, 날짜, 통화]
```

예:

```text
[비용값, 20260707, 'KRW']
```

Service Principal 인증과 Cost Management API 호출이 정상적으로 동작하고, 날짜별 실제 비용 데이터가 반환되는 것을 확인했다.

---

### 4. Resource Group 범위로 비용 조회 범위 변경

Subscription 전체 비용이 아닌 프로젝트 테스트 환경과 관련된 비용만 확인하기 위해 조회 Scope를 다음과 같이 변경했다.

```text
Subscription 전체
→ rg-finops-test Resource Group
```

현재 비용 수집 범위:

```text
/subscriptions/{subscription_id}/resourceGroups/{resource_group}
```

이를 통해 프로젝트 테스트 Resource Group에 포함된 리소스들의 비용을 중심으로 분석할 수 있도록 했다.

---

### 5. VM을 사용하지 않은 기간의 비용 원인 분석

비용 API 결과를 확인하던 중 VM을 실행하지 않았다고 생각한 기간에도 비용이 계속 발생하는 것을 확인했다.

일별 총비용만으로는 어떤 리소스에서 비용이 발생했는지 알 수 없었기 때문에 먼저 `ServiceName` 기준으로 비용을 그룹화했다.

확인된 서비스 범주:

```text
Storage
Virtual Network
Virtual Machines
Bandwidth
Log Analytics
```

이후 더 정확한 비용 발생 원인을 확인하기 위해 `ResourceId` 기준 그룹화도 추가했다.

```text
Grouping:
- ServiceName
- ResourceId
```

조회 결과를 통해 다음과 같이 비용 발생 리소스를 구분할 수 있었다.

```text
Storage
→ 테스트 VM의 OS Disk 관련 비용

Virtual Network
→ 테스트 VM 관련 Public IP 비용

Virtual Machines
→ 테스트 VM Compute 비용

Bandwidth
→ 네트워크 사용 관련 비용

Log Analytics
→ Log Analytics Workspace 관련 비용
```

확인 결과 VM Compute 비용이 0인 기간에도 Storage와 Virtual Network 관련 비용은 계속 발생할 수 있음을 확인했다.

이를 통해 VM을 사용하지 않는다고 해서 해당 VM과 관련된 모든 리소스의 비용이 자동으로 0이 되는 것은 아니라는 점을 알게 되었다.

### 6. `collect_cost()` 함수 구현

검증 코드에서 확인한 Cost Management API 호출 로직을 실제 Azure Collector에 통합했다.

`azure_exporter.py`에 다음 함수를 추가했다.

```text
collect_cost()
```

현재 비용 조회 조건:

```text
Scope:
rg-finops-test

Type:
ActualCost

Timeframe:
최근 7일

Granularity:
Daily

Aggregation:
Cost Sum

Grouping:
ServiceName
ResourceId
```

Azure Cost Management API의 반환 결과는 리스트 형태이므로 `columns`와 `rows`를 결합하여 Dictionary로 변환했다.

```python
rows = [
    dict(zip(columns, row))
    for row in (result.rows or [])
]
```

변환 전:

```text
[
    비용,
    날짜,
    서비스명,
    ResourceId,
    통화
]
```

변환 후:

```text
{
    "Cost": ...,
    "UsageDate": ...,
    "ServiceName": ...,
    "ResourceId": ...,
    "Currency": ...
}
```

이를 통해 배열 위치 번호가 아닌 실제 컬럼 이름으로 비용 데이터를 처리할 수 있도록 했다.

### 7. USD 변환 함수 구현

AWS, Azure, GCP의 비용 단위를 하나의 기준으로 비교하기 위해 USD 변환 기능을 추가했다.

함수:

```text
to_usd()
```

현재 개발 및 검증 단계의 고정 환율:

```text
1 USD = 1350 KRW
```

지원 통화:

```text
KRW
USD
```

예:

```text
1350 KRW
→ 1.0 USD
```

지원하지 않는 통화가 들어온 경우 잘못된 기본값을 사용하는 대신 다음 오류를 발생시키도록 했다.

```text
ValueError
```

이를 통해 알 수 없는 통화가 잘못된 USD 값으로 저장되는 것을 방지했다.

---

### 8. 공통 비용 레코드 변환 함수 구현

Azure Cost Management API의 원본 데이터를 팀 공통 비용 형식으로 변환하기 위해 다음 함수를 추가했다.

```text
to_common_cost_record()
```

현재 출력 구조:

```text
cloud
date
cost_usd
currency
service
granularity
```

날짜 형식도 다음과 같이 변환했다.

```text
20260707
→ 2026-07-07
```

출력 예:

```json
{
  "cloud": "azure",
  "date": "2026-07-07",
  "cost_usd": 0.088,
  "currency": "USD",
  "service": "Storage",
  "granularity": "DAILY"
}
```

현재 비용 공통 스키마는 팀 공통 비용 스키마 합의 전의 임시 구조이다.

팀 회의에서 변경 사항이 발생하면 차주 계획을 시작하기 전에 `to_common_cost_record()`와 관련 테스트를 수정할 예정이다.

## 막힌 점

### 1. VM을 사용하지 않은 기간에도 비용이 조회됨

초기 Cost Management API 조회 결과에서 VM을 사용하지 않았다고 생각한 기간에도 일별 비용이 발생하고 있었다.

날짜별 총비용만으로는 원인을 확인할 수 없었기 때문에 다음 순서로 조회 구조를 확장했다.

```text
날짜별 총비용
↓
ServiceName 기준 그룹화
↓
ResourceId 기준 그룹화
```

그 결과 VM Compute 비용과 별도로 OS Disk 및 Public IP 관련 비용이 지속적으로 발생할 수 있음을 확인했다.

이 과정을 통해 단순 총비용뿐 아니라 서비스와 리소스 기준 비용 분석이 필요하다는 것을 알게 되었다.

### 2. 비용 데이터를 자원 메트릭과 어떻게 연결할지 결정하지 않음

현재 자원 데이터는 다음과 같은 시점 기반 메트릭이다.

```text
CPU
Memory
Disk
VM Spec
```

비용 데이터는 다음과 같은 일별 데이터이다.

```text
Date
Cost USD
Service
Granularity
```

두 데이터의 집계 기준이 다르기 때문에 현재는 별도 레코드로 출력하고 있다.

팀 공통 비용 스키마 합의 이후 자원과 비용 데이터의 연결 기준을 최종 결정할 예정이다.

### 3. 팀 공통 비용 스키마 합의가 아직 완료되지 않음

현재 Azure 비용 공통 레코드는 다음 임시 구조를 사용한다.

```text
cloud
date
cost_usd
currency
service
granularity
```

팀 회의에서 AWS, Azure, GCP 비용 데이터 구조를 비교한 뒤 변경점이 발생하면 차주 계획 시작 전에 다음 항목을 함께 수정할 예정이다.

```text
to_common_cost_record()
비용 관련 단위 테스트
Runbook 공통 비용 필드 설명
```
