## 왜 이 기술/방법을 선택했는가
| 항목 | 선택한 것 | 대안 | 선택 이유 |
|------|-----------|------|-----------|
| EC2 접속 방식 | EC2 Instance Connect (브라우저) | SSH + pem 키 | 보유한 pem(`mission-key`)이 이 인스턴스의 키(`wjh61734-key`)와 불일치. 재발급보다 Instance Connect가 즉시 해결 |
| docker compose 실행체 | standalone `docker-compose` 바이너리 | `docker compose`(플러그인) | AL2023 저장소에 `docker-compose-plugin` 패키지가 없어 설치 실패 → GitHub 릴리스 바이너리로 대체 |
| 서버 이미지 빌드 | `DOCKER_BUILDKIT=0`으로 구형 빌더 사용 | buildx 플러그인 설치 | buildx 바이너리 다운로드 URL이 유효하지 않아 실패(9바이트만 받아짐). 빌드 자체가 급했던 상황이라 구형 빌더로 즉시 우회 |
| t3.micro 메모리 대응 | 스왑 파일 2GB 추가 | 인스턴스 타입 업그레이드 | 무료/저비용 유지가 우선. 테스트 규모 트래픽엔 스왑으로 충분 |
| 합성 데이터 저장 위치 (논의만, 미실행) | `data/synthetic/`에 CSV 분리 (검토) | DB `resource_metrics`에 label 컬럼 추가 | 진짜 수집 데이터와 합성 데이터가 한 테이블에 섞이면 8주차 대시보드가 오염됨. 스키마 변경 없이 진행 가능해 팀 합의 부담도 적음 → 미팅에서 별도 논의하기로 보류 |

## 오늘 처음 안 사실
| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |
|-----------|-----------|----------------|
| upsert가 왜 반영이 안 됐었는지 | UNIQUE 제약(DB)과 `ON CONFLICT`(서버 코드) 둘 다 있어야 동작함 | 지난 계획서엔 "처리함"이라 적혀 있었지만 실제 `main.py`엔 `INSERT`만 있었음. 제약만 걸면 재전송 시 500 에러, 코드만 있으면 애초에 막을 게 없음 |
| EC2 요금 단위 | Linux 온디맨드는 초 단위 과금(최소 60초), 30분/1시간 단위 아님 | 2017년부터 AWS가 EC2/EBS를 초당 과금으로 전환. t3.micro는 프리티어 시 월 750시간까지 무료 |
| GCP/GitHub clone인데 왜 안 열렸는지 | 같은 레포를 두 폴더(`~/CloudFit`, `~/Desktop/CloudFit`)에 각각 clone해둔 상태였음 | 브라우저 다운로드 파일을 실수로 다른 작업 폴더에 넣어서 발생. git 추적 밖의 로컬 상태(브랜치·Docker 볼륨)가 폴더별로 달라 병합이 아니라 파일 복사로 해결해야 했음 |
| 429 에러가 나도 서버 데이터가 안전한 이유 | 클라이언트(수집기) 쪽 API 실패와 서버 쪽 저장은 별개 단계 | Azure Cost Management API가 rate limit(429)으로 일부 요청을 거부해도, 성공한 요청들은 upsert를 거쳐 서버에 중복 없이 쌓임. 실패는 "데이터 손실 가능성"이지 "중복 저장"과는 무관 |

## 막힌 점
- 보안그룹 인바운드 규칙 추가 시 IAM 사용자(`wjh61734-collector`) 권한 부족(`UnauthorizedOperation`) → AWS 콘솔(웹)에서 직접 처리해 우회
- SSH 접속 시 키페어 불일치로 `Permission denied (publickey)` → 인스턴스 세부정보에서 실제 키페어명(`wjh61734-key`) 확인, 해당 pem 부재 → EC2 Instance Connect로 전환
- `docker-compose up --build` 시 `compose build requires buildx` 에러 → buildx 설치 시도했으나 릴리스 URL 문제로 실패 → `DOCKER_BUILDKIT=0`으로 우회하여 빌드 성공
- 실데이터 전송 중 비용 POST에서 read timeout 발생 → 원인은 t3.micro 메모리 부족(스왑 없음)으로 추정, 스왑 2GB 추가 후 재해결
- 로컬 작업 폴더가 두 곳(`~/CloudFit`, `~/Desktop/CloudFit`)에 중복 존재해 파일 반영이 엉뚱한 경로로 들어감 → 향후 `~/Desktop/CloudFit` 정리 필요 (오늘은 보류)
