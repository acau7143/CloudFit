# 2026-07-07 — Day 05-B

## 오늘 목표

- Azure VM의 메모리/디스크 사용률을 수집할 수 있도록 Azure Monitor Agent 기반 수집 구조를 구성한다.
- Log Analytics Workspace의 `Perf` 테이블에서 메모리/디스크 데이터를 확인한다.
- Python 코드에서 Log Analytics Workspace를 조회하여 `memory_percent`, `disk_percent` 값을 추출한다.
- 기존 `collectors/azure_exporter.py`에 메모리/디스크 수집 기능을 통합한다.
- `--dry-run`으로 CPU, 메모리, 디스크가 모두 공통 JSON 형식으로 출력되는지 검증한다.

## 오늘 한 일

- Azure VM `vm-finops-azure-test`를 실행 상태로 전환했다.
- Azure Monitor Agent가 VM에 설치되어 있는지 확인했다.
- Azure Monitor Agent 확장 설치를 완료했다.
  - Extension: `AzureMonitorLinuxAgent`
  - Publisher: `Microsoft.Azure.Monitor`
  - ProvisioningState: `Succeeded`
- Log Analytics Workspace `law-finops-test`를 생성했다.
- Data Collection Rule `dcr-finops-azure-vm`을 생성했다.
- DCR을 테스트 VM `vm-finops-azure-test`와 연결했다.
- DCR의 Performance Counter 데이터 원본에 메모리/디스크 카운터를 추가했다.
  - `Memory(*)\% Used Memory`
  - `Memory(*)\Available MBytes Memory`
  - `Logical Disk(*)\% Used Space`
  - `Logical Disk(*)\% Free Space`
- Log Analytics Workspace의 `Perf` 테이블에서 실제 메모리/디스크 데이터가 들어오는 것을 확인했다.
- `azure-monitor-query` 패키지를 설치했다.
- Workspace ID를 확인하고 `.env`에 `AZURE_LOG_WORKSPACE_ID`를 추가했다.
- `azure_log_check.py`를 작성하여 Python에서 LAW의 `Perf` 테이블을 직접 조회했다.
- 처음 실행 시 `AttributeError: 'str' object has no attribute 'name'` 오류가 발생했다.
- `table.columns` 처리 방식을 수정하여 오류를 해결했다.
- `azure_log_check.py`에서 `memory_percent`, `disk_percent` 추출에 성공했다.
- 기존 `collectors/azure_exporter.py`에 `LogsQueryClient` 기반 메모리/디스크 조회 기능을 추가했다.
- `py collectors\azure_exporter.py --dry-run`을 실행하여 CPU, 메모리, 디스크가 모두 공통 JSON으로 출력되는 것을 확인했다.

## 왜 이 기술/방법을 선택했는가

| 항목 | 선택한 것 | 대안 | 선택 이유 |
|------|-----------|------|-----------|
| 메모리/디스크 수집 방식 | Azure Monitor Agent + DCR + LAW | SSH 접속 후 `free`, `df` 명령 실행 | SSH 명령은 수동 확인에는 가능하지만 자동 수집기 구조에는 적합하지 않다. 중앙 수집 구조와 재현성을 위해 AMA 기반 방식을 선택했다. |
| 저장/조회 위치 | Log Analytics Workspace `Perf` 테이블 | Azure Portal VM 화면 수동 확인 | 수집 데이터를 Python 코드에서 자동 조회하려면 KQL로 조회 가능한 Workspace가 필요하다. |
| Python 조회 SDK | `azure-monitor-query` | Azure CLI 호출, REST API 직접 호출 | Python 수집 모듈 안에 통합해야 하므로 SDK 기반 조회가 적합하다. |
| CPU 수집 방식 | Azure Monitor Metrics API | LAW Perf 테이블로 통일 | CPU는 Azure 기본 플랫폼 메트릭으로 이미 정상 수집되고 있으므로 기존 구조를 유지했다. |
| 메모리/디스크 수집 방식 | LAW `Perf` 테이블 조회 | 기존 `azure-mgmt-monitor` metrics API만 사용 | 메모리/디스크는 guest OS 내부 지표이므로 AMA와 DCR을 통해 Perf 테이블에 적재한 뒤 조회하는 방식이 적합하다. |
| 검증 방식 | `--dry-run` JSON 출력 | DB 저장 후 확인 | 아직 중앙 서버/DB 연동 전 단계이므로, 서버 전송 없이 수집 결과를 공통 형식으로 확인하는 `--dry-run`이 안전하다. |
| 장애 기록 방식 | fail/recovery 캡처 저장 | 성공 화면만 저장 | 실패 원인과 복구 결과를 함께 남겨야 같은 문제가 반복될 때 빠르게 원인을 찾을 수 있다. |

## 오늘 처음 안 사실

| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |
|-----------|-----------|----------------|
| Azure VM 메모리/디스크가 기본 메트릭으로 바로 나오지 않을 수 있다는 점 | CPU는 플랫폼 메트릭으로 바로 조회 가능하지만, 메모리/디스크는 guest OS 내부 지표라 AMA 설정이 필요하다. | 메모리와 파일시스템 사용률은 VM 내부 운영체제에서 관측되는 값이므로 Azure 플랫폼 외부에서 에이전트를 통해 수집해야 한다. |
| AMA, DCR, LAW의 역할 차이 | AMA는 수집 실행 주체, DCR은 수집 규칙, LAW는 저장 및 조회 위치이다. | VM에 에이전트만 설치해도 어떤 데이터를 어디로 보낼지 규칙이 없으면 데이터가 쌓이지 않는다. |
| Query Hub와 Query Editor의 차이 | Query Hub는 예제/저장 쿼리 모음이고, 실제 KQL 실행은 Query Editor에서 한다. | Query Hub는 쿼리를 찾거나 재사용하기 위한 도구이고, 데이터 조회 결과는 Log Analytics 쿼리 실행 결과로 확인한다. |
| `Perf` 테이블 구조 | `ObjectName`, `CounterName`, `InstanceName`, `CounterValue` 조합으로 성능 데이터가 저장된다. | 하나의 테이블 안에 메모리, 디스크 등 여러 성능 카운터가 함께 들어오기 때문에 조건으로 필요한 값을 골라야 한다. |
| `table.columns` 처리 방식 | 현재 설치된 `azure-monitor-query 2.0.0`에서는 `table.columns`가 문자열 목록이다. | 기존에 `.name` 속성으로 접근하려고 해서 문자열에 존재하지 않는 속성을 호출하는 오류가 발생했다. |
| 루트 디스크 사용률 선택 기준 | `CounterName == "% Used Space"`이고 `InstanceName == "/"`인 값을 사용했다. | Linux VM에서는 여러 파일시스템이 존재하므로, 전체 VM 기준 대표 디스크 사용률로 루트 파일시스템(`/`)을 우선 사용했다. |
| Python 들여쓰기 중요성 | 함수 내부 코드가 밖으로 빠지면 문법 오류 또는 실행 오류가 발생한다. | Python은 중괄호가 아니라 들여쓰기로 코드 블록을 구분하기 때문이다. |

## 막힌 점

- `azure_log_check.py` 실행 중 `AttributeError: 'str' object has no attribute 'name'` 오류가 발생했다.
  - 원인: `table.columns`가 이미 문자열 목록인데, 코드에서 `column.name`으로 접근했다.
  - 해결: `columns = list(table.columns)`로 수정했다.

- `azure_exporter.py` 수정 중 들여쓰기 문제가 발생할 수 있었다.
  - 원인: 메모장에서 수정하면서 함수 내부 코드의 공백이 사라질 수 있었고, 일부 줄에는 탭이 섞일 수 있었다.
  - 해결: 함수 내부는 공백 4칸 기준으로 맞추고, 실행 전 코드 구조를 다시 확인했다.

- `.env`에는 인증 정보와 Workspace ID가 들어 있으므로 캡처 또는 Git 업로드 시 주의가 필요하다.
  - 해결: `.env`는 `.gitignore`로 제외하고, 캡처 시 비밀값이 화면에 보이지 않도록 주의한다.
