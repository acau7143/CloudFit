# 2026-07-02 — Day 02-B

## 오늘 목표

- Azure 수집기가 사람 계정 로그인 없이 API를 호출할 수 있도록 Service Principal을 생성한다.
- `.env` 파일에 Azure 인증 정보를 저장하고, `.gitignore`로 GitHub 업로드를 방지한다.
- 로컬 PC에 Python 실행 환경과 Azure SDK를 설치한다.
- Service Principal 인증이 실제로 성공하는지 확인한다.
- Azure Monitor API로 테스트 VM의 CPU 사용률을 조회한다.
- `stress-ng`로 VM에 CPU 부하를 생성하고, 부하 전후 CPU 수치가 달라지는지 검증한다.
- 작업 종료 후 VM을 중지(할당 취소)하여 불필요한 비용 발생을 막는다.

## 오늘 한 일

- Azure Cloud Shell에서 현재 구독 정보를 확인했다.
  - `SubscriptionId`
  - `TenantId`
  - 구독 이름
- `finops-collector` Service Principal을 생성했다.
  - 역할: `Monitoring Reader`
  - 범위: `rg-finops-test` 리소스 그룹
- 출력된 `appId`, `password`, `tenant` 값을 `.env` 파일에 저장했다.
- `.gitignore`에 `.env`를 추가하여 인증 정보가 GitHub에 올라가지 않도록 설정했다.
- `dir -Force`로 `.env`, `.gitignore` 파일이 생성된 것을 확인했다.
- `git status`에서 `.env`가 표시되지 않는 것을 확인했다.
- 로컬 Windows 환경에 Python과 pip를 설치했다.
  - Python 버전: `3.14.6`
  - pip 버전: `26.1.2`
- Azure SDK 관련 패키지를 설치했다.
  - `azure-identity`
  - `azure-mgmt-monitor`
  - `python-dotenv`
- `azure_auth_check.py`를 작성하여 Service Principal 인증을 확인했다.
  - `ClientSecretCredential`로 토큰 발급 성공
- `azure_cpu_check.py`를 작성하여 Azure Monitor에서 `Percentage CPU` 메트릭을 조회했다.
- 처음에는 `timespan` 시간 형식 오류가 발생했다.
  - `datetime.isoformat()` 출력 형식이 Azure Monitor API가 요구하는 형식과 맞지 않았다.
  - UTC 시간을 `YYYY-MM-DDTHH:MM:SSZ` 형식으로 변환하여 해결했다.
- CPU 메트릭 수집에 성공했다.
  - 초기 CPU 값은 대부분 0%대였고, VM 시작 직후 구간에서만 약간 높게 나왔다.
- SSH 접속을 시도했으나 private key 권한 오류가 발생했다.
  - Windows에서 `.pem` 파일 권한이 너무 열려 있어 SSH가 키 사용을 거부했다.
  - `icacls`로 현재 사용자만 읽을 수 있도록 권한을 제한하여 해결했다.
- SSH로 Azure VM에 접속했다.
  - 접속 계정: `azureuser`
  - 대상 VM: `vm-finops-azure-test`
- VM 내부 Ubuntu에서 `stress-ng`를 설치했다.
- `stress-ng --cpu 2 --timeout 300s --metrics-brief` 명령어로 5분 동안 CPU 부하를 생성했다.
- 부하 이후 Azure Monitor API를 다시 호출하여 CPU 사용률 상승을 확인했다.
  - 부하 후 CPU 평균값이 약 `91.9983%`까지 상승했다.
- 테스트 종료 후 VM을 중지(할당 취소)했다.

| 항목 | 선택한 것 | 대안 | 선택 이유 |

| 권한 범위 | `rg-finops-test` 리소스 그룹 범위 | 구독 전체 범위 | 테스트 VM이 들어 있는 리소스 그룹에만 권한을 주는 것이 최소 권한 원칙에 더 가깝다. |
| 역할 | `Monitoring Reader` | `Reader`, `Contributor` | 오늘 목표는 CPU 메트릭 조회이므로 모니터링 데이터 읽기 권한만 우선 부여했다. |
| 비밀값 저장 | `.env` | 코드에 직접 입력, 메모장 별도 관리 | 코드에 인증 정보를 직접 쓰면 GitHub 업로드 시 유출 위험이 있으므로 `.env`에 분리했다. |
| Git 보호 | `.gitignore`에 `.env` 추가 | 매번 수동으로 조심 | 실수로 `git add .`를 해도 `.env`가 올라가지 않도록 자동으로 방지하기 위해 사용했다. |
| Python 패키지 설치 | `python -m pip install ...` | `pip install ...` | 로컬에서 `pip` 명령어가 처음에는 인식되지 않았으므로 Python 모듈 방식으로 pip를 실행하는 것이 더 안정적이었다. |
| Azure SDK | `azure-identity`, `azure-mgmt-monitor` | Azure CLI 명령어만 사용 | 이후 수집 모듈을 Python 코드로 작성해야 하므로 SDK 기반 호출이 필요했다. |
| CPU 메트릭 | `Percentage CPU` | 메모리, 디스크 메트릭 | CPU는 Azure Monitor 기본 메트릭으로 바로 조회하기 쉬워 첫 API 호출 검증 대상으로 적합했다. |
| 부하 생성 | `stress-ng` | 직접 무한 루프 스크립트 작성 | 짧은 명령어로 CPU 부하를 안정적으로 만들 수 있고, 실행 시간도 쉽게 제한할 수 있기 때문이다. |
| 검증 방식 | 부하 전후 CPU 값 비교 | CPU 값 1개만 출력 | 단순 출력보다 부하를 걸었을 때 값이 실제로 변하는지 확인하는 것이 수집기의 신뢰성을 더 잘 보여준다. |
| 종료 방식 | VM 중지(할당 취소) | 실행 상태 유지, VM 삭제 | 실행 상태로 두면 비용이 발생하고, 삭제하면 다음 실습 대상이 사라지므로 할당 취소가 적절했다. |

## 오늘 처음 안 사실

| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |
|-----------|------------|------------------|
| Service Principal의 역할 | Azure API를 호출하는 프로그램용 계정이라는 것을 알게 되었다. | 사람 계정으로 매번 로그인하지 않고, 코드가 정해진 권한으로 Azure 리소스에 접근해야 하기 때문이다. |
| `appId`, `password`, `tenant`의 의미 | `appId`는 client ID, `password`는 client secret, `tenant`는 tenant ID로 사용된다. | Azure SDK의 `ClientSecretCredential`이 이 세 값을 사용해 토큰을 발급받기 때문이다. |
| password가 바뀐 이유 | `az ad sp create-for-rbac`를 다시 실행하면 password가 새로 출력될 수 있다. | Service Principal 생성 또는 credential 재생성 과정에서 새 secret이 발급될 수 있기 때문이다. |
| `.env`와 `.gitignore`의 관계 | `.env`는 로컬에 존재하지만 Git에는 올라가지 않게 할 수 있다. | `.gitignore`에 `.env`를 추가하면 Git이 해당 파일을 추적하지 않기 때문이다. |
| Python PATH 문제 | `python`, `pip`, `py` 명령어가 처음에는 제대로 잡히지 않을 수 있다. | Windows에 Python 런타임이 설치되어 있지 않거나 PATH 연결이 안 되어 있으면 터미널에서 명령어를 찾지 못하기 때문이다. |
| Azure Monitor 시간 형식 | Azure Monitor API의 `timespan`은 ISO 8601 형식에 맞춰야 한다. | 잘못된 시간 문자열을 넘기면 API가 조회 구간을 해석하지 못하고 `BadRequest`를 반환한다. |
| UTC timestamp | Azure Monitor에서 출력되는 시간은 한국 시간이 아니라 UTC 기준이다. | 출력의 `+00:00`은 UTC를 의미하며, 한국 시간은 UTC보다 9시간 빠르기 때문이다. |
| 5분 평균 CPU | `interval="PT5M"`와 `aggregation="Average"`는 5분 단위 평균 CPU를 의미한다. | Azure Monitor가 지정한 시간 간격마다 메트릭을 집계해서 반환하기 때문이다. |
| VM 시작 직후 CPU 상승 | VM을 켠 직후에는 CPU가 일시적으로 높을 수 있다. | Ubuntu 부팅, cloud-init, 네트워크 설정, 백그라운드 서비스 초기화가 발생하기 때문이다. |
| VM Agent 경고 | VM Agent 경고가 떠도 기본 CPU 메트릭 조회는 가능할 수 있다. | `Percentage CPU`는 Azure 플랫폼 메트릭이고, guest OS 내부 세부 지표와는 구분되기 때문이다. |
| SSH private key 권한 | `.pem` 파일 권한이 너무 열려 있으면 SSH가 키를 거부한다. | private key는 다른 사용자가 읽을 수 없어야 하므로 SSH 클라이언트가 보안을 위해 사용을 막는다. |
| stress-ng 동작 방식 | `stress-ng --cpu 2 --timeout 300s`는 CPU worker 2개를 5분 동안 실행한다. | CPU에 인위적인 연산 부하를 만들어 Azure Monitor에서 사용률 상승을 확인할 수 있다. |

## 막힌 점

- `pip` 명령어가 처음에 인식되지 않았다.
  - 원인: 로컬 PC에 Python 런타임과 pip가 제대로 설치되어 있지 않았거나 PATH가 설정되지 않았다.
  - 해결: Python 설치 관리자에서 CPython을 설치하고, 새 PowerShell에서 `python --version`, `python -m pip --version`으로 확인했다.

- Azure SDK 설치 중 PATH 관련 WARNING이 출력되었다.
  - 원인: 일부 보조 실행 파일 경로가 PATH에 포함되어 있지 않았다.
  - 해결: 오늘 작업에는 Python 코드 실행만 필요하므로 문제 없이 진행했다.

- Azure Monitor CPU 조회 시 `BadRequest` 오류가 발생했다.
  - 원인: `timespan` 값의 시간 형식이 Azure Monitor API 요구 형식과 맞지 않았다.
  - 해결: UTC 시간을 `YYYY-MM-DDTHH:MM:SSZ` 형식으로 변환하여 다시 요청했다.

- VM 상태 화면에서 “VM 에이전트 상태가 준비되지 않았습니다” 경고가 표시되어 VM이 꺼진 것으로 착각했다.
  - 원인: VM Agent 상태 경고와 VM 실행 상태를 혼동했다.
  - 해결: VM 상태가 `실행 중`인지 별도로 확인했고, CPU 메트릭 조회는 정상적으로 수행되었다.

- SSH 접속 시 private key 권한 오류가 발생했다.
  - 원인: `.pem` 파일 권한이 너무 열려 있어 SSH 클라이언트가 키 사용을 거부했다.
  - 해결: `icacls` 명령어로 상속 권한을 제거하고 현재 사용자에게만 읽기 권한을 부여했다.
