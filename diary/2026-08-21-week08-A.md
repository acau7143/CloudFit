- **`ml/train.py`**: `fetch_training_data()` 쿼리에 `AND source = 'real'` 조건 추가
- **`ml/anomaly_detector.py`**:
  - 조회 쿼리(평소 1시간 구간 + `--full` 전체 구간 둘 다)에 동일하게 `source = 'real'` 필터 적용
  - `--full` 옵션 추가 — 평소엔 최근 1시간만 보던 걸, 과거 오염분을 일괄 재계산할 때 전체 real 데이터를 훑을 수 있게 함
  - `INSERT ... ON CONFLICT DO NOTHING` → `DO UPDATE`로 변경. 기존 방식은 같은 `(cloud, instance_id, timestamp)`가 이미 저장돼 있으면 재탐지해도 절대 덮어쓰지 않아서, 모델을 고쳐도 과거 오염된 결과가 DB에 영구히 남는 문제가 있었음
- **재학습 + 재탐지**: real 데이터(8,509건)로 재학습 → `--full`로 전체 재탐지 실행. AWS/Azure/GCP 모두 이상 비율이 학습 시 설정한 `contamination=0.05`에 맞게 약 5.0%로 정상화됨
- **`db/schema.sql` 동기화**: EC2 DB에 `source`, `pattern` 컬럼과 `idx_resource_metrics_source` 인덱스가 이미 있었는데 `schema.sql`엔 반영이 안 되어 있던 걸 발견 → 문서화. (실제 `ALTER TABLE`이 언제 누구에 의해 실행됐는지는 확인 못 함 — 다음 팀 미팅에서 공유 필요)

## 왜 이 기술/방법을 선택했는가
| 항목 | 선택한 것 | 대안 | 선택 이유 |
|------|-----------|------|-----------|
| 오염된 과거 `anomaly_results` 처리 | `ON CONFLICT DO UPDATE`로 바꾸고 `--full` 재계산 | `TRUNCATE` 후 처음부터 재탐지 | TRUNCATE는 되돌릴 수 없는 삭제이고 탐지 이력 자체가 사라짐. DO UPDATE는 원본 `resource_metrics`는 그대로 두고 `anomaly`/`score`만 최신 모델 기준으로 덮어써서, 데이터 손실 없이 오염만 제거 가능 |
| synthetic 재발 방지 | `anomaly_detector.py` 쿼리에도 `source` 필터 추가 | train.py만 수정 | train.py만 고치면 모델 자체는 정상이 되지만, 10분 크론이 여전히 synthetic 데이터까지 탐지 대상에 넣고 있어서 문제가 다시 재발함. 탐지 쿼리도 같이 고쳐야 함 |
| `db/schema.sql` 갱신 방식 | 실제 EC2 DB 상태를 확인 후 문서만 맞춤 | EC2에 로컬 schema.sql을 그대로 적용 | EC2 DB에 이미 `source`/`pattern` 컬럼과 데이터가 존재하는 상태라, 반대로 적용하면 기존 컬럼과 충돌 위험. `CREATE TABLE IF NOT EXISTS` 구조라 문서만 갱신해도 안전하고 실제 DB엔 영향 없음 |

## 오늘 처음 안 사실
| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |
|-----------|-----------|----------------|
| 모델을 재학습하면 DB의 과거 탐지 결과도 자동으로 최신화되는 줄 알았음 | `ON CONFLICT DO NOTHING` 구조에서는 같은 타임스탬프 행이 이미 있으면 재탐지 결과가 저장 자체가 안 됨 | 재탐지 크론이 "최근 1시간"만 훑는 구조라, 이미 저장된 과거 타임스탬프는 몇 번을 다시 돌려도 갱신되지 않고 옛날 값 그대로 남음 |
| 로컬 리포와 EC2 DB가 항상 같은 스키마인 줄 알았음 | EC2에서 직접 `ALTER TABLE`로 컬럼을 추가하면 `schema.sql`엔 반영 안 된 채로 둘이 어긋날 수 있음 | `docker-compose`로 DB를 새로 띄우는 게 아니라 기존 컨테이너에 계속 붙어서 작업하다 보니, 스키마 변경이 코드(schema.sql)가 아니라 DB에만 직접 가해진 상태였음 |

## 막힌 점
- 여러 줄 heredoc(`python3 << 'PYEOF' ... PYEOF`)으로 파일 수정 시도 중 한 번은 반영이 안 되고(같은 `cat` 결과만 반복 출력됨), 원인이 명확히 재현되진 않음 → 파일 전체를 base64로 인코딩해서 한 줄 명령어로 덮어쓰는 방식으로 우회해 해결. 다만 이 방식은 사람이 눈으로 diff를 안 보면 뭐가 바뀌는지 확인이 안 되는 단점이 있어, 다음부턴 heredoc을 기본으로 쓰고 실패할 때만 base64로 전환하기로 함
- `anomaly_results`에 `ON CONFLICT DO NOTHING`이 걸려있어서, 모델을 고쳐도 과거 오염된 탐지 결과가 자동으로 안 바뀌는 걸 뒤늦게 발견 → `DO UPDATE` + `--full` 옵션 추가로 해결
