## 오늘 한 일

### 1) synthetic 데이터 오염 수정
- **원인 확인**: `resource_metrics`를 `cloud`, `source`별로 집계 → synthetic 데이터가 클라우드당 17,282건씩 있는데, real은 AWS 1,806 / Azure 1,743 / GCP 4,959건뿐. 학습 시 `source` 필터가 없어서 synthetic이 real을 압도해 모델이 실제 서버 패턴이 아니라 합성 패턴을 "정상"으로 학습하고 있었음
- `ml/train.py`: `fetch_training_data()` 쿼리에 `AND source = 'real'` 조건 추가
- `ml/anomaly_detector.py`:
  - 조회 쿼리(평소 1시간 구간 + `--full` 전체 구간 둘 다)에 동일하게 `source = 'real'` 필터 적용
  - `--full` 옵션 추가 - 과거 오염분을 일괄 재계산할 때 전체 real 데이터를 훑을 수 있게 함
  - `INSERT ... ON CONFLICT DO NOTHING` → `DO UPDATE`로 변경. 기존 방식은 같은 (cloud, instance_id, timestamp)가 이미 저장돼 있으면 재탐지해도 절대 덮어쓰지 않아서, 모델을 고쳐도 과거 오염된 결과가 DB에 영구히 남는 문제가 있었음
- 재학습(real 8,509건) + `--full` 재탐지 실행. AWS/Azure/GCP 모두 이상 비율이 contamination=0.05에 맞게 약 5.0%로 정상화됨
- `db/schema.sql`: EC2 DB에 이미 있던 source, pattern 컬럼과 idx_resource_metrics_source 인덱스를 문서에 반영 (실제 DB엔 있었는데 schema.sql엔 누락돼 있던 상태)

### 4) Grafana 대시보드 - 비용 추천 패널 추가 (8주차 목표)
- Grafana는 UI 프로비저닝 없이 도커 볼륨(grafana_data)에 상태를 저장하는 구조라, dashboard/dashboard.json 파일을 고쳐도 자동 반영은 안 됨을 확인
- Grafana HTTP API(/api/dashboards/db)로 기존 대시보드(uid adl2nrn, 기존 패널 5개)에 새 패널을 직접 추가:
  - "비용 최적화 추천 (클라우드별 최신)" 테이블 패널 - recommendations 테이블에서 클라우드별 최신 1건만 조회, recommendation 값에 따라 배경색 매핑(downsize=orange, keep=green, terminate=red)
  - 기존 5개 패널(CPU/비용/이상탐지) 위치는 그대로 두고, 빈 그리드 자리(x=12, y=16)에 배치
- 브라우저로 직접 접속해서 6개 패널 전부 정상 렌더링 확인 - 특히 이상탐지 패널의 빨간 점(anomaly)이 CPU 튀는 구간에만 정확히 찍혀있어 오늘 고친 모델이 실제로 잘 작동하는 걸 시각적으로 재확인
- 최신 상태(패널 6개, version 10)를 API로 다시 조회해 dashboard/dashboard.json에 재export, GitHub에도 백업

## 왜 이 기술/방법을 선택했는가
| 항목 | 선택한 것 | 대안 | 선택 이유 |
|------|-----------|------|-----------|
| 오염된 과거 anomaly_results 처리 | DO UPDATE + --full 재계산 | TRUNCATE 후 처음부터 재탐지 | TRUNCATE는 되돌릴 수 없는 삭제이고 탐지 이력이 사라짐. DO UPDATE는 원본은 그대로 두고 anomaly/score만 갱신해서 데이터 손실 없이 오염만 제거 |
| 비용 추천 조인 기준 | cloud 단위 조인 | cost_records에 instance_id 추가 | 클라우드당 인스턴스가 실제로 1개씩이라 cloud 기준으로도 정확도 손실 없음. 오늘 안에 끝내야 해서 스키마 변경 없이 진행 |
| Grafana 패널 반영 방식 | HTTP API로 직접 추가 | dashboard.json 수정 후 재시작 | Grafana가 도커 볼륨에 상태를 저장하는 구조라 파일 수정만으론 반영 안 됨 |
| schema.sql 갱신 방식 | EC2 DB 상태 확인 후 문서만 맞춤 | 로컬 schema.sql을 EC2에 적용 | EC2 DB에 이미 컬럼과 데이터가 존재해 반대로 적용하면 충돌 위험 |

## 오늘 처음 안 사실
| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |
|-----------|-----------|----------------|
| 재학습하면 DB의 과거 탐지 결과도 자동 최신화되는 줄 알았음 | ON CONFLICT DO NOTHING 구조에서는 같은 타임스탬프 행이 있으면 재탐지 결과가 저장 자체가 안 됨 | 재탐지 크론이 최근 1시간만 훑는 구조라 과거 타임스탬프는 갱신 안 됨 |
| 로컬 리포와 EC2 DB가 항상 같은 스키마인 줄 알았음 | EC2에서 직접 ALTER TABLE하면 schema.sql엔 반영 안 된 채로 어긋날 수 있음 | 스키마 변경이 코드가 아니라 DB에만 직접 가해진 상태였음 |
| 크론이 매일 정상 실행되면 기능도 정상인 줄 알았음 | 내부 API 호출이 매번 실패해도 로그에만 남고 3주간 조용히 누적될 수 있음 | 실패를 감지하는 헬스체크/알림이 없었기 때문 |
| Grafana 대시보드는 JSON 파일 하나로 관리되는 줄 알았음 | 프로비저닝 없이 UI로 만든 대시보드는 도커 볼륨 안 내부 DB에 저장되고, 리포의 JSON은 내보내기 스냅샷일 뿐임 | docker-compose.yml에 프로비저닝 볼륨 마운트가 없어서 파일 기반 자동 로드 구조가 아니었음 |
