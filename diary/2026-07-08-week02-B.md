## 오늘 목표

- Azure Compute API를 이용하여 테스트 VM의 인스턴스 타입, vCPU 수, RAM 용량을 자동으로 수집한다.
- 기존 `azure_exporter.py`에 CPU, 메모리, 디스크, VM 사양 수집 기능을 모두 통합한다.
- `to_common_record()`를 현재 공통 필드 기준으로 확장한다.
- 단위 테스트를 3개 이상 작성하여 공통 데이터 변환 기능을 검증한다.
- `stress-ng`를 이용하여 저활용, 정상 사용, 과부하 상태의 CPU 패턴을 생성하고 Azure Monitor에서 확인한다.
- 기존에 분리되어 있던 Azure Collector Runbook과 Guest Metrics Runbook을 하나의 최신 Runbook으로 통합한다.

## 오늘 한 일

### 1. Azure Compute SDK 설치 및 VM 사양 수집

- Azure VM 사양 정보를 Python에서 조회하기 위해 `azure-mgmt-compute` 패키지를 설치했다.
- 설치 후 `azure-mgmt-compute 38.1.0`이 정상적으로 설치된 것을 확인했다.
- `azure_exporter.py`에 `ComputeManagementClient`를 추가했다.
- `query_vm_spec()` 함수를 작성하여 다음 정보를 조회하도록 구현했다.
  - VM Size
  - vCPU 수
  - RAM 용량
- VM 사양을 코드 내부의 고정 매핑 테이블로 관리하지 않고 Azure Compute API의 VM 정보와 Resource SKU capability 정보를 이용해 조회하도록 구성했다.
- 실제 테스트 VM에서 다음 사양을 확인했다.

```text
instance_type: Standard_B2ats_v2
vcpu: 2
ram_gb: 1.0
```

### 2. azure_exporter.py 전체 기능 통합

기존 Azure Collector는 다음 기능을 각각 추가해 온 상태였다.

```text
CPU
→ Azure Monitor Metrics API

Memory / Disk
→ AMA → DCR → LAW → Perf

VM Spec
→ Azure Compute API
```

이번 작업에서 위의 결과를 `collect_resource_metrics()`에서 하나의 raw 데이터로 합치고, `to_common_record()`를 통해 공통 JSON 형식으로 출력하도록 통합했다.

최종 공통 출력 필드는 다음과 같다.

```text
cloud
resource_id
resource_type
region
timestamp
cpu_percent
memory_percent
disk_percent
instance_type
vcpu
ram_gb
cost_monthly
source
```

비용 수집은 아직 구현하지 않았기 때문에 현재는 다음과 같이 처리했다.

```text
cost_monthly: null
```

`--dry-run` 실행 결과 CPU, 메모리, 디스크, VM 사양 정보가 모두 정상적으로 출력되는 것을 확인했다.

### 3. 단위 테스트 확장

기존 Day 04 테스트는 CPU 중심의 초기 공통 레코드만 검증하고 있었기 때문에 현재 Collector 구조에 맞게 테스트를 확장했다.

다음 4개의 테스트를 작성했다.

```text
1. 전체 공통 필드가 정상적으로 전달되는지 확인
2. memory_percent와 disk_percent가 None이어도 정상 처리되는지 확인
3. 0.0 값을 None으로 잘못 처리하지 않는지 확인
4. 내부 처리용 metric_name 필드가 공통 레코드에서 제거되는지 확인
```

실행 명령어:

```powershell
py -m unittest -v tests.test_azure_exporter
```

실행 결과:

```text
Ran 4 tests

OK
```

모든 테스트가 정상적으로 통과했다.

### 4. stress-ng CPU 부하 패턴 생성

Azure Monitor에서 서로 다른 CPU 사용 패턴이 구분되는지 확인하기 위해 `stress-ng`를 사용했다.

실험은 다음 순서로 진행했다.

```text
10% 부하 10분
→ 휴식 5분
→ 55% 부하 10분
→ 휴식 5분
→ 90% 부하 10분
→ 휴식 5분
```

사용한 명령어:

```bash
stress-ng --cpu 0 --cpu-load 10 --timeout 600s
```

```bash
stress-ng --cpu 0 --cpu-load 55 --timeout 600s
```

```bash
stress-ng --cpu 0 --cpu-load 90 --timeout 600s
```

각 부하 구간 사이에 5분의 휴식 시간을 두어 Azure Monitor 그래프에서 세 패턴의 경계가 구분되도록 했다.

Azure Monitor의 `Percentage CPU` 그래프에서 낮은 부하, 중간 부하, 높은 부하 구간이 순서대로 구분되는 것을 확인했다.

### 5. stress-ng 실행 후 Collector 재검증

부하 테스트가 끝난 뒤 SSH 세션을 종료하고 로컬 PowerShell에서 다시 Collector를 실행했다.

```powershell
py collectors\azure_exporter.py --dry-run
```

CPU, 메모리, 디스크, VM 사양 정보가 모두 정상적으로 출력되는 것을 확인했다.

이를 통해 stress-ng 부하 테스트 이후에도 Azure Collector가 정상 동작하는 것을 확인했다.

## 왜 이 기술/방법을 선택했는가

| 항목 | 선택한 것 | 대안 | 선택 이유 |
|------|-----------|------|-----------|
| VM 사양 수집 | Azure Compute API + Resource SKU capability | VM Size별 사양을 코드에 직접 매핑 | VM 종류가 추가되거나 변경될 때 코드의 매핑 테이블을 계속 수정하지 않아도 되며 실제 Azure 정보를 기준으로 조회할 수 있다. |
| VM 정보 조회 | `ComputeManagementClient` | Azure Portal에서 수동 확인 | Collector가 자동으로 VM 사양을 수집해야 하므로 Python SDK 방식이 적합하다. |
| 공통 데이터 변환 | `to_common_record()` 유지 및 필드 확장 | 각 수집 함수에서 바로 최종 JSON 생성 | 클라우드별 원본 데이터 수집과 공통 스키마 변환을 분리하면 구조를 이해하고 수정하기 쉽다. |
| 단위 테스트 | Python `unittest` | 수동으로 dry-run 결과만 확인 | API를 매번 호출하지 않고도 공통 데이터 변환 규칙이 깨지지 않았는지 빠르게 확인할 수 있다. |
| 0.0 테스트 | 실제 숫자 0과 `None`을 구분 | `if value` 형태의 단순 조건 | 사용률 0.0은 정상 데이터이므로 데이터 없음 상태인 `None`과 구분해야 한다. |
| CPU 패턴 생성 | `stress-ng` | 직접 CPU 부하 스크립트 작성 | 목표 부하율을 간단한 명령어로 변경할 수 있고 반복 실험이 쉽다. |
| 부하 패턴 사이 휴식 | 각 단계 사이 5분 대기 | 3개 명령을 연속 실행 | Azure Monitor 그래프에서 각 부하 구간의 경계를 쉽게 구분할 수 있다. |
| Runbook 관리 | 최신본 1개 + 주차별 이전 버전 보관 | 기능별 Runbook을 계속 분리 | 현재 전체 실행 절차는 한 문서에서 확인하면서도 주차별 변화 과정은 별도로 남길 수 있다. |

## 오늘 처음 안 사실

| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |
|-----------|-----------|----------------|
| VM Size 이름만으로 vCPU와 RAM을 어떻게 자동 확인하는지 | VM의 `hardware_profile.vm_size`를 확인하고 Resource SKU capability에서 `vCPUs`, `MemoryGB` 값을 조회할 수 있다. | VM Size 이름과 실제 하드웨어 사양 정보가 Azure Compute Resource SKU 정보에 포함되어 있기 때문이다. |
| VM 사양 매핑 테이블을 꼭 직접 만들어야 하는지 | Azure API에서 실제 사양 정보를 조회하면 수동 매핑 없이도 VM 사양을 수집할 수 있다. | 수동 매핑은 새로운 VM Size가 추가될 때 코드 수정이 필요하지만 API 조회 방식은 실제 Azure 정보를 기준으로 동작한다. |
| `0.0`과 `None`을 테스트해야 하는 이유 | `0.0`은 실제 측정값이고 `None`은 데이터가 없다는 뜻이므로 서로 다른 값이다. | Python에서 단순히 `if value`를 사용하면 `0.0`도 False로 처리되어 데이터가 없는 것으로 잘못 판단할 수 있다. |
| 단위 테스트와 dry-run의 차이 | 단위 테스트는 함수의 데이터 변환 규칙을 자동 검증하고, dry-run은 실제 Azure API를 통한 전체 수집 흐름을 검증한다. | 두 검증 방식의 범위가 다르므로 함께 사용해야 코드 로직과 실제 API 연동을 각각 확인할 수 있다. |
| 목표 CPU 부하와 Azure Monitor 값이 완전히 같지 않을 수 있다는 점 | `stress-ng`의 목표 부하율과 실제 Azure Monitor 그래프 값은 정확히 일치하지 않을 수 있다. | 운영체제 스케줄링, 기존 시스템 부하, Azure Monitor의 집계 방식 등이 결과에 영향을 줄 수 있기 때문이다. |
| 부하 패턴 사이에 휴식 구간이 필요한 이유 | 각 부하 구간 사이에 낮은 사용률 구간을 만들면 그래프에서 패턴을 쉽게 구분할 수 있다. | 연속된 부하 테스트만 실행하면 수집 및 집계 결과가 이어져 단계별 경계가 흐려질 수 있기 때문이다. |
| Runbook과 Diary의 역할 차이 | Runbook은 현재 다시 따라 할 수 있는 최신 절차이고 Diary는 실제 작업 과정을 시간순으로 기록하는 문서이다. | Runbook에 주차별 작업 기록을 계속 추가하면 최신 실행 절차를 찾기 어려워질 수 있기 때문이다. |

## 막힌 점

### 1. VM 사양을 어떤 방식으로 관리할지 고민함

초기 계획에서는 VM Size에 따른 vCPU와 RAM 정보를 Python 딕셔너리에 직접 작성하는 방식을 고려했다.

예:

```python
VM_SPECS = {
    "Standard_B1s": {
        "vcpu": 1,
        "ram_gb": 1
    }
}
```

하지만 VM Size가 추가되거나 변경되면 코드를 계속 수정해야 한다는 문제가 있었다.

이를 해결하기 위해 Azure Compute API에서 실제 VM Size를 조회하고 Resource SKU capability를 통해 `vCPUs`와 `MemoryGB`를 가져오는 방식으로 구현했다.

### 2. 기존 단위 테스트가 현재 Collector 구조와 맞지 않음

기존 테스트용 raw 데이터에는 다음 필드가 없었다.

```text
instance_type
vcpu
ram_gb
cost_monthly
```

현재 `to_common_record()`가 위 필드를 처리하도록 확장되었기 때문에 테스트 코드도 현재 공통 레코드 형식에 맞춰 수정했다.

기존 1개 테스트를 다음 4개 테스트로 확장했다.

```text
전체 필드 전달
None 처리
0.0 값 유지
내부 metric_name 제거
```

### 3. stress-ng 패턴 구분 방법

세 가지 부하 명령을 연속으로 실행하면 Azure Monitor 그래프에서 경계를 명확하게 구분하기 어려울 수 있다고 판단했다.

각 부하 단계 사이에 5분간 부하를 주지 않는 휴식 구간을 만들어 다음과 같이 진행했다.

```text
10% → 휴식 → 55% → 휴식 → 90% → 휴식
```

결과적으로 Azure Monitor 그래프에서 서로 다른 세 단계의 CPU 패턴을 확인할 수 있었다.
