## 오늘 한 일
- `compute_v1.DisksClient()` / `AddressesClient()`로 연결 안 된 디스크, 미사용 예약 IP 탐지하는 `collectors/gcp_unused_detector.py` 작성
- 처음엔 DB(asyncpg)에 직접 연결하는 방식으로 짰다가, GCP 인스턴스에서 실행하니 `localhost:5432` 접속 실패 발생
- 원인 파악: DB는 AWS EC2 컨테이너 안에 있는데, GCP에서 `localhost`는 GCP 자기 자신을 가리킴 → 애초에 설계가 잘못됨
- 기존 `gcp_exporter.py`가 쓰던 방식(`SERVER_URL` + `requests.post()`로 중앙 서버에 HTTP 요청)을 그대로 따라가도록 수정
- `docker-compose restart`로 반영이 안 돼서 원인 파악 → `docker-compose.yml`의 `server:`에 `volumes` 없이 `build`만 있어서 코드가 이미지 빌드 시점에 고정된다는 걸 확인
- 실제 GCP 테스트 디스크로 탐지 → 서버 전송 → DB 저장까지 전 구간 검증 성공

## 왜 이 기술/방법을 선택했는가
| 항목 | 선택한 것 | 대안 | 선택 이유 |
|------|-----------|------|-----------|
| 서버 통신 방식 | HTTP POST (`SERVER_URL`) | asyncpg 직접 DB 연결 | GCP↔AWS는 다른 머신이라 `localhost`로 못 붙음. 기존 수집기들과 패턴 통일 |
| Docker 이미지 빌드 | `DOCKER_BUILDKIT=0 docker build` (레거시 빌더) | `docker-compose build` (buildx) | 서버에 buildx가 없거나 버전이 낮아 빌드 자체가 실패함 |
| 엔드포인트 설계 | `cloud`를 요청 본문 필드로 받는 공통 엔드포인트 1개 | 클라우드별 엔드포인트 3개 | 기존 `/resources`, `/costs`와 동일한 공통 스키마 원칙 유지, AWS/Azure도 그대로 재사용 가능 |

## 오늘 처음 안 사실
| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |
|-----------|-----------|----------------|
| `docker-compose restart`가 코드 변경을 반영해줄 거라 생각함 | `restart`는 컨테이너를 껐다 켜는 것뿐, 이미지 재빌드가 아님 | `server:` 서비스가 `volumes` 없이 `build`만 있어서, 코드가 이미지 빌드 시점에 COPY되어 고정됨  |
