# 2026-08-04 — Day 11 (GCP 담당)

> 5주차(서버 정식 전환 + stress-ng 데이터 + 팀 코드 감사) 

## 오늘 목표
- `SERVER_URL`을 ngrok 임시 주소에서 EC2 정식 주소(`.env` 기반)로 교체하고 재검증
- stress-ng로 정상/이상 패턴 데이터를 생성해서 DB에 쌓기 (ML 준비용 스모크 테스트)

## 오늘 한 일
- `gcp_exporter.py`에서 `SERVER_URL` 하드코딩 제거 → `python-dotenv`로 `.env`에서 읽도록 수정, ngrok 헤더(`ngrok-skip-browser-warning`)도 더 이상 필요 없어서 제거
- 실전송 실행 → 자원 데이터 1건, 비용 데이터 43건 서버에 전송 성공 (`curl`로 확인)
- stress-ng로 정상(`--cpu 1`)/이상(`--cpu 4`) 패턴을 각각 5분씩 만들고 수집기 실행 → `cpu_avg`가 33.08% vs 33.2%로 거의 차이가 안 나는 걸 발견. Cloud Monitoring 콘솔에서는 순간 CPU가 최대 ~380%까지 튄 걸 눈으로 확인했는데도 수집된 평균값에는 거의 안 잡힘
- 이 희석 문제를 지금 당장 구간을 좁혀서 고칠지 검토했으나, `project-plan.md` 5주차에 합성 데이터 생성기가 별도로 예정돼 있고 오늘 한 건 어차피 정식 ML 학습용이 아니라 스모크 테스트라서 지금은 보류, 7주차 ML 설계 때 다시 다루기로 함
- `aws_exporter.py` / `azure_exporter.py` / `gcp_exporter.py` 세 개를 직접 대조해서 CPU/메모리/디스크 평균 구간이 실제로 통일돼 있는지 확인 → **Azure의 CPU만 30분, 나머지(Azure 메모리·디스크 포함 전부)는 1시간**이라는 불일치 발견
- 통일이 더 필요한 항목들을 정리: 측정 구간(Azure CPU 30→60분), cloud 값 대소문자, `cost_monthly` 필드 처리 방식, `cpu_avg` None 방어 로직, timestamp 포맷(`Z` vs `+00:00`), 서버 전송 코드 구조 차이
- 발표 시연 중 API 429(Too Many Requests) 대응을 위해 재시도 로직 검토 → Azure Monitor Metrics API가 제일 취약하고, AWS Cost Explorer도 위험도 높음, CloudWatch/GCP Monitoring은 상대적으로 낮다는 걸 확인.

## 왜 이 기술/방법을 선택했는가

| 항목 | 선택한 것 | 대안 | 선택 이유 |
|------|-----------|------|-----------|
| stress-ng 라벨명 | `normal` / `anomaly` (영문 소문자 고정) | 한글 라벨, `abnormal` | `ml/anomaly_detector.py` 모듈명과 용어를 맞추고, 대소문자·인코딩 문제를 미리 방지 |
| 음수 비용(크레딧) 처리 | DB엔 원본 그대로 저장, Grafana 대시보드에서만 색상으로 구분 표시 | 0으로 클램프해서 저장 | 클램프하면 월 합계(SUM)가 실제 지출보다 부풀려짐. 비용 데이터의 정확성이 FinOps 도구의 핵심 가치라 원본 보존이 우선 |
| 평균 구간 희석 문제 | 지금 안 고치고 7주차로 미룸 | 오늘 바로 구간 좁혀서 재수집 | 진짜 ML 학습 데이터는 5주차 합성 데이터 생성기/외부 데이터셋에서 올 예정. 오늘 건 스모크 테스트라 과잉대응 방지 |

## 오늘 처음 안 사실

| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |
|-----------|-----------|----------------|
| 1시간 평균이면 5분짜리 부하도 눈에 띄게 잡힐 줄 알았음 | 5분 스파이크가 1시간 평균에 묻혀서 정상/이상 구분이 거의 안 됨(33.08% vs 33.2%) | 평균은 전체 구간 값을 합쳐서 나눈 값이라, 짧은 구간의 극단값이 나머지 55분의 평상시 값에 희석됨 |
| Azure도 GCP/AWS처럼 CPU·메모리·디스크 전부 1시간 평균인 줄 알았음 | Azure만 CPU 조회 구간이 30분(`DEFAULT_LOOKBACK_MINUTES = 30`)이고, 메모리·디스크는 Azure도 1시간이라 Azure 내부에서도 안 맞음 | Azure Monitor의 CPU 쿼리(`query_cpu_metric`)와 Log Analytics 기반 메모리·디스크 쿼리(`query_guest_metrics`)가 서로 다른 함수로 짜여 있어서 구간 값이 따로 놀았음 |
| Azure/AWS SDK도 429를 알아서 다 재시도해줄 줄 알았음 | SDK마다 기본 재시도 정책과 대상 예외가 달라서, Azure Monitor·AWS Cost Explorer처럼 원래 쿼터가 빡빡한 API는 기본 재시도만으론 부족할 수 있음 | azure-core, botocore, google-api-core가 각자 재시도할 예외 종류·횟수를 다르게 정의해놔서 |

- 3개 클라우드 수집기 코드 직접 대조로 Azure CPU 30분 불일치 확인
