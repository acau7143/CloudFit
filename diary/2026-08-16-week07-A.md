## 왜 이 기술/방법을 선택했는가
| 항목 | 선택한 것 | 대안 | 선택 이유 |
|------|-----------|------|-----------|
| 이상탐지 모델 구조 | **클라우드별 모델 분리** (3개 모델을 1개 pkl에 저장) | 클라우드 내 정규화 후 단일 모델 | 구현이 단순하고 결과 해석이 명확함. 클라우드별 분포 형태 차이로 인한 왜곡 위험도 적음 |
| anomaly_results UNIQUE 제약 | `(cloud, instance_id, timestamp)` | 제약 없음 | 10분 크론이 "최근 1시간" 데이터를 매번 다시 조회하므로, 제약 없으면 겹치는 구간이 중복 저장됨 |
| 이미지 빌드 방식 | `docker build` 직접 실행 후 `docker-compose up -d` | `docker-compose up -d --build` | compose의 빌드 단계가 buildx 최신 버전을 요구해 실패, build와 up을 분리해 우회 |
| GitHub 인증 | SSH 키 | Personal Access Token | 서버(EC2) 하나에서 지속적으로 이 repo에만 접근하는 상황이라, 토큰 만료 관리 없이 한 번 등록으로 계속 쓸 수 있는 SSH가 더 적합 |
| 파일 수정 방식 | Python 스크립트(문자열 라인 매칭 치환) | heredoc(`cat >> ... << EOF`) | 원격 터미널에서 긴 코드 블록 붙여넣기 시 heredoc 종료 토큰 인식이 여러 번 꼬여서, 좀 더 안전한 방식으로 전환 |

## 오늘 처음 안 사실
| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |
|-----------|-----------|----------------|
| 이상탐지 모델은 이상치만 잘 잡으면 되는 줄 알았음 | **입력 피처에 그룹(클라우드) 간 스케일 차이가 크면, 모델이 이상 패턴이 아니라 그룹 자체를 학습**해버릴 수 있음 | Isolation Forest는 피처 공간의 "드묾"을 기준으로 판단하므로, 그룹 간 절대값 차이가 크면 그 차이 자체가 가장 두드러진 신호가 되어버림 |
| AWS가 100% 이상으로 뜬 게 버그인 줄 알았음 | p10(하위 10%)·중앙값과 비교해보니 **실제로 평소보다 낮은 CPU 사용 구간이 지속**된 것이 원인 — 정상적인 탐지 결과였음 | score와 백분위수를 같이 봐야 "모델 문제"와 "실제 이상 상황"을 구분할 수 있음 |
| GitHub이 비밀번호로 push를 막아둔 지 몰랐음 | 2021년부터 **HTTPS + 비밀번호 인증 자체가 차단**, PAT나 SSH 키만 가능 | 계정 탈취 시 비밀번호 하나로 전체 계정이 뚫리는 위험을 줄이기 위한 정책 |
| pip 옵션(`--break-system-packages`)이 항상 되는 줄 알았음 | **pip 23.1 이상부터** 지원되는 옵션이라, EC2의 pip 21.3.1에선 인식 안 됨 | Amazon Linux는 Debian 계열과 달리 시스템 패키지 보호(PEP 668)를 강제하지 않아 이 옵션 자체가 불필요 |
