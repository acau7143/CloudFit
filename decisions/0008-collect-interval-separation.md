# 0008 - Azure Cost Management API 429 대응: 재시도 vs 호출 인터벌 분리

## Context

Azure Cost Management API는 스코프(subscription/resource group)당 **분당 4회 호출 제한**이 있다 (INC-001, 기존 known issue로 문서화됨).

`azure_exporter.py`는 `--dry-run` 또는 실제 전송(`run_send()`) 실행 시 자원 메트릭 수집과 비용 수집을 같은 실행 안에서 연달아 호출하는 구조라, 짧은 시간 안에 반복 실행하면(특히 발표 시연이나 디버깅 중 재실행) 429 에러가 발생할 수 있다.

429가 발생하면 `collect_cost()`가 예외를 던지며 즉시 중단되고, 자원 데이터는 이미 전송됐더라도 비용 데이터만 누락되는 상황이 반복됐다.

## Decision

1단계로 `collect_cost()`에 **429 전용 재시도 로직**을 추가한다 (`max_retries=3`, `Retry-After` 헤더 기반 대기).

단, 이 재시도는 **완화책**이며 **호출 빈도 자체를 줄이는 근본 해결책(자원/비용 수집 인터벌 분리)은 별도 작업으로 백로그에 남긴다.**

## Why

- 재시도는 구현이 간단하고, 발표 시연처럼 "당장 안 죽으면 되는" 상황에 즉시 효과가 있다.
- 하지만 재시도는 "분당 4회 제한"이라는 원인 자체를 없애지 않는다. 짧은 간격으로 계속 실행하면 재시도 3번을 다 쓰고도 여전히 429가 날 수 있다.
- 진짜 원인 제거는 호출 자체를 줄이는 것 — 예를 들어 자원 메트릭은 5분마다, 비용 데이터는 1시간마다처럼 **수집 주기를 분리**하면 애초에 분당 4회에 걸릴 일이 줄어든다.
- 이번 주(Week07)는 429 재시도(완화)와 stress-ng 부하 패턴 생성이 우선순위라, 인터벌 분리(해결)는 이번 주 범위에서 제외하고 별도 일정으로 미룬다.

## 대안과의 비교

| 방식 | 원인 해결 여부 | 구현 난이도 | 효과 |
|------|--------------|------------|------|
| 재시도(현재 채택, 1단계) | 완화만 | 낮음 | 즉시 적용 가능, 시연 중단 방지 |
| 호출 인터벌 분리(미정, 2단계) | 해결 | 중간 (수집 주기 재설계 필요) | 429 발생 빈도 자체를 낮춤 |
| 호출 자체를 캐싱/배치로 묶기 | 해결 | 높음 | 과설계 우려, 현재 프로젝트 규모엔 과함 |

## Result

- `collect_cost()`에 429 감지 + `Retry-After` 기반 대기 + 최대 3회 재시도 로직 추가 완료
- 로컬 검증(`--dry-run` 반복 실행)에서 429 발생 → 재시도 → 정상 복구 확인 (`evidence/week07-azure-429-retry-ok.png`)
- **후속 작업으로 남김**: 자원/비용 수집 인터벌 분리 — 아직 일정 미정. 이번 주(Week07) 계획엔 포함되어 있지 않으며, 별도 백로그로 관리
