# 0002. 비용 데이터 테이블 분리 및 그룹핑 단위 결정

## Context
3주차부터 비용(cost) 데이터 수집이 추가되면서, 이걸 기존
`resource_metrics` 테이블에 합칠지 별도 테이블로 만들지,
그리고 하루치 비용을 어떤 단위로 저장할지 결정 필요.

## Decision
1. `resource_metrics`와 `cost_records`를 별도 테이블로 분리한다.
2. `cost_records`는 하루 총합 1행이 아니라, **서비스별로 여러 행**으로 저장한다.
3. GCP 수집기의 `service.description LIKE '%Compute%'` 필터는 제거하고,
   Compute 외 모든 서비스(Storage, Network 등) 비용도 수집한다.

## Why

**테이블 분리 이유**

| 항목 | 자원 메트릭 | 비용 데이터 |
|------|------------|------------|
| 수집 주기 | 5분 간격 | 하루 1회 |
| 단위 | % | USD |
| 조회 방식 | 현재 시점 기준 | 날짜 범위 기반 |

한 테이블에 합치면 비용 컬럼(`cost_usd` 등)이 대부분의 행에서
NULL로 남고, 조회 시 자원 데이터와 비용 데이터를 매번 걸러내야 하는
번거로움이 생김.

**서비스별 그룹핑 이유**
프로젝트의 핵심 목표(이상탐지, 비용 최적화 추천)는 "어떤 서비스 때문에
비용이 늘었는지" 알아야 의미가 있음. 하루 총합 1행으로는 이 판단이
불가능하고, 서비스별로 나뉘어 있어야 저장소/네트워크/컴퓨트 중
어디서 비용이 튀었는지 구분 가능함.

**Compute 필터 제거 이유**
`cost_records`는 인스턴스 단위가 아니라 계정 전체 단위 데이터이므로,
Compute 비용만 보면 실제 지출의 일부만 파악하게 되는 문제가 있음.
Azure 코드(필터 없음)와 비교했을 때, GCP만 Compute로 범위가 좁아
전체 지출 파악이 불가능한 상태였음.

## 대안과의 비교
| 대안 | 문제점 |
|------|--------|
| 한 테이블에 통합, nullable 컬럼 추가 | 수집 주기가 달라 대부분 행에 NULL 발생, 쿼리 복잡도 증가 |
| 클라우드별로 테이블 분리 (aws_costs, azure_costs, gcp_costs) | 팀원 늘어날 때마다 테이블 증가, 통합 분석 쿼리가 UNION 필요 |
| 하루 총합 1행으로 통일 | 서비스별 원인 분석이 불가능해 이상탐지/추천 기능 구현에 부적합 |
| Compute 필터 유지 | 전체 지출의 일부만 파악, Storage/Network 비용 누락 |

## Result
- `resource_metrics`, `cost_records` 두 테이블로 분리 확정 (`db/schema.sql` 반영 완료)
- `cost_records` 그룹핑 단위를 서비스별 여러 행(Azure 방식)으로 통일
- `collectors/gcp_exporter.py`의 `collect_cost()`, `to_common_cost_record()`에
  서비스별 그룹핑 반영 및 Compute 필터 제거 완료

**남은 작업**: AWS(A)는 3주차 비용 수집을 아직 시작 안 해서, 착수 시
이 방식(서비스별 그룹핑, 전체 서비스 포함)을 기준으로 구현 필요.
