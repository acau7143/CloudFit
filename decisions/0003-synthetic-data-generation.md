# 0003 — ML 학습용 합성(synthetic) 데이터 생성

## Context
7주차부터 Isolation Forest 기반 이상탐지 모델을 학습시킬 계획인데, 그 시점까지 cron으로 쌓인 real 데이터는 클라우드당 몇백~몇천 건 수준이었고 그마저도 대부분 "정상" 상태(평상시 CPU)뿐이었다. 이상탐지 모델이 "이상"을 구분하려면 과부하·스파이크·점진적 증가 같은 비정상 패턴도 학습 데이터에 있어야 하는데, 실제 서버에서 그런 패턴이 자연 발생하길 기다리기엔 시간이 부족했다.

## Decision
`resource_metrics`에 `source`(`real`/`synthetic`)와 `pattern`(정상/저활용/과부하/스파이크/점진적증가) 컬럼을 추가하고, `data/synthetic/generate_synthetic.py`로 가짜 인스턴스 6개(클라우드별 2개)에 30일치 5분 간격 데이터를 생성해 `source='synthetic'`으로 삽입했다.

- 패턴별 가중치 랜덤이 아니라, **인스턴스 6개 중 처음 5개는 5개 패턴에 하나씩 고정 배정**하고 나머지 1개만 랜덤 배정 → 가중치가 낮은 패턴(스파이크, 점진적증가)이 우연히 하나도 안 뽑히는 상황을 방지
- 결과: 총 51,846건 (정상 17,282 / 저활용·과부하·스파이크·점진적증가 각 8,641건)

## Why
- 모델이 "정상"만 보고 학습하면 이상탐지 자체가 성립하지 않음 — 최소한 다양한 비정상 패턴의 존재는 알아야 함
- `pattern` 정답 라벨을 직접 부여할 수 있다는 게 가장 큰 이유였음: Isolation Forest는 비지도학습이라 원래 "모델이 맞았는지"를 확인할 방법이 없는데, synthetic 데이터는 우리가 정답을 알고 만들었기 때문에 나중에 모델 정확도 검증에도 재사용 가능
- `source` 컬럼으로 구분해두면 real 데이터가 쌓인 뒤에는 언제든 synthetic 비중을 줄이거나 제외할 수 있음 (확장성 확보)

## 대안과의 비교
| 대안 | 장점 | 단점 | 채택 여부 |
|------|------|------|-----------|
| 실제 데이터가 자연스럽게 쌓일 때까지 대기 | 가장 현실적인 데이터 | 이상 패턴이 언제 발생할지 예측 불가, 프로젝트 기간(15주) 내 확보 어려움 | 미채택 |
| 외부 공개 데이터셋(Azure Public Dataset 등) 사용 | 검증된 실제 데이터 | 우리 프로젝트의 인스턴스 스펙·클라우드 구성과 안 맞음, 스키마 변환 필요, 정답 라벨이 우리가 정의한 패턴과 다름 | 미채택 (`data/external/`에 보조 자료로만 남김) |
| 직접 합성 데이터 생성기 작성 (채택) | 원하는 패턴을 정확히 통제 가능, 정답 라벨 직접 부여 → 검증에도 재사용 가능, 언제든 재생성 가능 | 실제 서버 특성과 분포가 다를 수 있음 (→ 실제로 이 부작용이 INC-002로 나타남) | **채택** |

## Result
- `resource_metrics`에 51,846건의 synthetic 데이터 확보, 5개 패턴 전부 대표성 있게 생성됨
- 다만 클라우드별 real 데이터의 실제 CPU 평균과 synthetic 평균의 격차가 컸음 (AWS 7.6배, Azure 70배, GCP 2배) — `ml/train.py`가 `source` 구분 없이 이 데이터를 그대로 학습에 사용하면서 모델이 왜곡되는 부작용 발생 ([INC-002](../incidents/INC-002 — ML 이상탐지 오탐 (synthetic 데이터 오염).md) 참고)
