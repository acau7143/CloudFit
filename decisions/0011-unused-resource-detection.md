## Azure 파트 (B)

### Context

FinOps Framework의 "Optimize(낭비 제거)" 영역을 채우기 위해, Azure 환경에서
어떤 리소스에도 안 붙어있는(그런데 계속 과금되는) 관리 디스크·공인 IP를
탐지해야 함. 지금까지 파이프라인(`resource_metrics`)은 VM 단위 사용률만
보고 있어서, VM이 지워진 뒤에도 남는 디스크·IP는 완전히 사각지대였음.

### Decision

- **판정 기준**
  - 관리 디스크: `disk_state == 'Unattached'` 정확히 매칭
  - 공인 IP: `ip_configuration is None`
- **스캔 범위**: subscription 전체가 아니라 `AZURE_RESOURCE_GROUP` 하나로 한정
  (`disks.list_by_resource_group`, `public_ip_addresses.list(resource_group)` 사용)
- **확정 방식**: 판정된다고 바로 확정(알림)하지 않고, 서버에 이미 활성 상태로
  남아있는 이전 탐지 기록과 대조해서 같은 `resource_id`가 다시 나오면 그때
  "확정"으로 보고 Slack 알림을 보냄. 최초 탐지는 서버에 저장만 하고 알림은 보류.

### Why

- **`Unattached`만 정확히 매칭한 이유**: `disk_state`엔 `Unattached` 외에도
  `Attached`, `Reserved`(정지된 VM에 붙어있음), `Frozen`, `ActiveSAS` 등이
  있음. `Reserved`는 VM이 잠깐 꺼져있을 뿐 미사용이 아니므로, "Attached가
  아니면 미사용"처럼 부정형으로 판정하면 오탐이 생김. 정확히 `Unattached`
  문자열과 일치할 때만 미사용으로 본다.
- **리소스 그룹으로 스캔 범위를 한정한 이유**: subscription 전체를 스캔하면
  권한이 없는 다른 리소스 그룹은 에러 없이 빈 목록만 돌아올 수 있어
  ("미사용 리소스 없음"으로 착각하는 오탐 패턴). 또한 이미 있는
  aws_exporter(REGION 고정), gcp_exporter(ZONE 고정)와 스코프 컨벤션을
  통일하는 게 팀 전체 일관성 측면에서 낫다고 판단.
- **재탐지 확정 방식을 도입한 이유**: 공인 IP 리소스(`PublicIPAddress`)엔
  생성 시각을 확인할 수 있는 필드가 아예 없음(Azure Python SDK 문서로 확인).
  그래서 "방금 만든 IP"와 "오래 방치된 IP"를 생성 시각 기준으로 구분할 수
  없고, 하나 걸렸다고 바로 확정하면 방금 만든 IP도 오탐될 위험이 있음.
  대신 스키마 변경 없이 기존 `detected_at`/`resolved_at`만으로, "여러 번
  연속 탐지될 때만 확정"하는 방식을 택함.

### 대안과의 비교

| 대안 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| Azure Advisor Recommendations API로 대체 | Azure가 이미 계산해줌, 구현 간단 | 팀 공통 패턴(직접 SDK 조회)과 어긋남, 판정 기준을 Azure 블랙박스에 위임 | 미채택 |
| subscription 전체 스캔 | 여러 리소스 그룹에 흩어진 리소스까지 탐지 가능 | 권한 범위 확장 필요, 오탐 위험(권한 없는 그룹은 빈 목록), 팀 컨벤션과 불일치 | 미채택 |
| 생성 시각 기준 유예 기간(예: "생성 후 1시간 이내는 제외") | 직관적 | 공인 IP 리소스에 생성 시각 필드 자체가 없어 구현 불가. Activity Log 별도 조회는 리소스당 추가 API 호출이 필요해 비용 큼 | 미채택 |
| 연속 탐지 시 확정 (서버의 기존 활성 목록과 클라이언트 측 대조) | 스키마·서버 API 변경 없음, A/서버 조율 불필요 | 탐지 주기가 뜸하면(예: 하루 1회 미만) 확정까지 시간이 걸림 | **채택** |

### Result

- 테스트용 공인 IP(`test-unused-ip`), 테스트용 데이터 디스크
  (`test-unused-disk`, VM에 붙였다가 분리)로 재현 테스트 진행.
- 1차 실행: 둘 다 `confirmed: false`(최초 탐지)로 서버에 저장됨. Slack
  알림 없음.
- 2차 실행: 서버의 이전 활성 목록에서 동일 `resource_id` 발견 →
  `confirmed: true`로 전환, Slack `#finops_alerts` 채널에 알림 도착 확인.
- 리소스 그룹 내 실제 사용 중인 디스크(OS 디스크)·공인 IP(VM에 연결된 IP)는
  탐지되지 않음을 Azure Portal에서 직접 확인 (오탐 아님 검증).
- 결론: 설계한 판정 기준·확정 방식이 의도대로 동작함을 확인. 알려진 한계는
  아래 참고.

### 알려진 한계

- 재탐지 확정 방식은 스캔이 뜸하게 실행되면(예: 하루 1회 미만) 실제
  방치 시간과 무관하게 확정까지 걸리는 시간이 길어질 수 있음. 지금
  프로젝트 범위(탐지만 하고 자동 삭제는 안 함, 최종 판단은 사람이 검토)
  에서는 치명적이지 않다고 보고 넘어감.
