# 0014. 이상탐지에 median/MAD 방식 병행 도입

## Context
기존 이상탐지(`ml/anomaly_detector.py`)는 `train.py`가 주 1회(매주 일요일 새벽 3시) 계산하는
정적 평균±3표준편차(3σ) 기준을 사용한다. 2026-09-27 실측 결과, Azure의 CPU 사용률이
한 주 사이 완만하게(0.71% → 0.85~0.89%) 이동했는데, 갱신 주기가 느려서(주 1회)
3σ의 좁은 표준편차(0.04)가 그 변화를 못 따라가 대량 오탐이 발생함을 확인
(Azure: 3σ 기준 이상 1443건 중 1250건(86.6%)이 MAD 기준으로는 정상).

## Decision
기존 3σ 판정 로직은 그대로 유지하고, median/MAD 기반 modified z-score 판정을 병행 도입한다.
- `is_out_of_range_mad()`: modified_z = 0.6745 × (x - median) / MAD, 임계값 3.5 (Iglewicz & Hoaglin)
- `fetch_rolling_baseline()`: train.py의 주 1회 갱신과 달리, 실행될 때마다(10분 주기)
  최근 7일 데이터로 매번 새로 median/MAD 계산 (rolling window)
- `anomaly_results`에 `cpu_anomaly_mad`, `mem_anomaly_mad`, `disk_anomaly_mad`, `anomaly_mad`
  컬럼 추가, 기존 3σ 결과와 나란히 저장해서 비교 가능하게 함
- Grafana "멀티클라우드 - 이상탐지" 대시보드에 `anomaly_point_mad` 시리즈 추가해 시각적 비교

## Why
- 평균/표준편차는 이상치 자체에 의해 값이 왜곡되는 masking 문제 있음 (breakdown point 0%)
- median/MAD는 breakdown point 50%로, 절반 이상이 오염돼야 망가질 만큼 이상치에 강함
- 갱신 주기를 주 1회 → 매 실행(10분)으로 바꿔서 baseline이 실제 트렌드를 빠르게 반영

## 대안과의 비교
| 대안 | 장점 | 단점 |
|------|------|------|
| 3σ 단독 유지 | 구현 단순 | baseline이 낡으면 대량 오탐 (실측으로 확인됨) |
| 3σ를 median/MAD로 완전 교체 | 로직 단순화 | 검증 없이 교체는 리스크 큼, Grafana 연동도 갈아엎어야 함 |
| **병행 도입 후 비교 (채택)** | 리스크 최소화, 실측 근거로 판단 가능 | 컬럼/코드가 일시적으로 늘어남 |

## Result
실제 라이브 데이터(40,108건)로 검증 완료.
- AWS: 3σ 8466건 vs MAD 8413건 (거의 일치 — baseline이 최신이라 큰 차이 없음)
- Azure: 3σ 1443건 vs MAD 193건 (3σ만 1250건 — 낡은 baseline발 오탐 확인)
- GCP: 3σ 449건 vs MAD 213건 (3σ만 236건 — 동일 패턴)

## 알려진 한계
`--full` 재실행 시 MAD 판정은 각 행의 원래 시점이 아니라 "재실행 시점 기준 최근 7일"로
baseline을 계산하기 때문에, 인프라 변경으로 정상 범위 자체가 바뀐 경우 과거 데이터가
잘못 이상으로 표시될 수 있다.

실제 사례: AWS 인스턴스 업그레이드로 디스크 용량이 증설되면서 사용률이 08/29~09/13
구간 ~95-100%에서 09/14 이후 ~40%대로 하락(정상적 변화). median/MAD 컬럼을 09/27에
처음 도입한 뒤 `--full`로 30일치를 소급 적용하자, 업그레이드 이전 구간 전체가
"오늘 기준" baseline과 비교되어 MAD 이상으로 잘못 표시됨.

평소 운영(크론 증분 실행, `--full` 없이)에서는 매 실행 시점 기준으로 baseline이
계산되므로 이 문제가 발생하지 않으며, 인스턴스 업그레이드 같은 실제 변화가 생기면
전환 시점에만 짧게 이상 신호를 내고 며칠 내 새 baseline에 재적응할 것으로 예상된다.
`--full`은 백필/디버깅 용도로만 제한적으로 사용할 것.

두 방식 병행 운영을 유지하며 추후 비교 지속.
